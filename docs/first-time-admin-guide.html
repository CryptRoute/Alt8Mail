Phase 01 · Preflight

Prepare the server and the names.

The installer is opinionated. Give it a fresh Debian 12 host, a public IPv4 address and working DNS, and the first installation is predictable. Solve the provider-level questions now, while nothing is live.

The commands in this guide assume a root shell. If you sign in with a sudo account, prefix host-level commands with sudo.

Server baseline

ItemRequirement
Operating systemDebian 12 (bookworm), 64-bit. The installer refuses other distributions.
Accessroot, or a sudo account that can become root.
CPU and RAM2 vCPU and 4 GB as a practical floor. Use 4 vCPU and 8 GB or more for production, then watch the dashboard under real load.
Disk50 GB minimum for evaluation. Size production for Maildirs, attachments, PostgreSQL growth, logs and backup headroom.
NetworkPublic IPv4 address plus control of the provider firewall and reverse DNS.
Host stateFresh host with no other mail or web stack. Take a provider snapshot first.

The installer adds a 2 GiB swap file when the host has less than 2 GiB of swap, sets the host time zone to UTC and sets the mail hostname. Keep UTC on the host; each user chooses their own time zone in the workspace.

Choose the five names

Mail domainexample.comThe domain in users' addresses. The owner address must end in @example.com.
Mail hostnamemail.example.comMX target and the name on the TLS certificate.
Tenant nameExample CorpDisplay name for the organization.
Tenant slugexampleLowercase letters, digits and hyphens. No spaces.
System Control emailsysadmin@example.comA separate login for the host control plane. It does not create a mailbox.

DNS before installation

If you want an automatic Let's Encrypt certificate, create both A records before running the installer. The installer requests one certificate covering the bare domain and the mail hostname.

TypeNameValueWhy
Amail.example.comYOUR_SERVER_IPV4Webmail, TLS and MX target
Aexample.comYOUR_SERVER_IPV4Part of the standard certificate request
PTR / rDNSYour server IPv4mail.example.comSet at the VPS provider; improves outbound reputation
CAAexample.comInclude letsencrypt.orgOnly if you already publish CAA; a restrictive record blocks issuance
Make the mail record DNS-only.If mail.example.com is behind Cloudflare or another HTTP proxy, it cannot carry SMTP or IMAP. Turn the proxy off for that record. If the bare domain has to stay with a different website, use a dedicated mail domain instead of forcing the standard certificate path.

Check the basics from your workstation:

bash · DNS preflight
dig +short A mail.example.com
dig +short A example.com
dig -x YOUR_SERVER_IPV4 +short
dig +short CAA example.com

Both A records should return the server address, and reverse DNS should return mail.example.com. once the provider has applied it. Keep the TTL low, between 300 and 3600 seconds, while you are setting this up.

Ports the installer expects

The installer configures UFW, but it cannot override a provider firewall. Open the same ports in the provider's security group.

PortPurposeWho needs it
22 / your SSH portAdministrationYou only
80ACME challenge and HTTP redirectPublic
443Webmail, customer admin, TLSPublic
25Inbound SMTPPublic; provider must allow it
587Authenticated submissionMail clients
993IMAPSMail clients
995POP3SMail clients that use POP
4190ManageSieveOptional; close it if unused
8808System ControlAdministrators only; root-equivalent
Confirm port 25 with the provider before you install.Ask for inbound and outbound TCP 25 to be open. UFW cannot fix an upstream block. Outbound 25 can be handled with a smarthost later; inbound 25 cannot, because remote mail servers must reach your MX directly.

Never expose PostgreSQL 5432, Redis 6379, the Go backends on 8080/8081, or System Control without an access restriction.

Preflight checklist

You are ready to install when the host, DNS and port 25 all answer correctly.

Phase 02 · Install

Run the installer once, then prove the stack.

Use the prebuilt release bundle when possible. It avoids a server-side Go build and gives you a checksum to verify before anything runs.

Upload and verify the release

Download the release bundle and its checksum from the repository's GitHub Releases page, then copy both to the server.

workstation · upload 0.3.12
scp alt8mail-0.3.12.tar.gz alt8mail-0.3.12.tar.gz.sha256 root@YOUR_SERVER_IP:/root/
server · verify and extract
cd /root
sha256sum -c alt8mail-0.3.12.tar.gz.sha256
tar -xzf alt8mail-0.3.12.tar.gz
cd alt8mail-0.3.12

If you are installing from a source checkout, use one of the private transfer paths below. Do not clone the private repository with an account password, and do not copy the development working tree to the server.

Private transfer from GitHub

Option A · The server pulls the tag from GitHub (recommended)

Create a repository-scoped deploy key on the server before running the installer. The installer reuses this key for future updates, so one credential covers both the initial clone and alt8mail-update.

server · create the deploy key
apt-get update && apt-get install -y git openssh-client
install -d -m 0755 /etc/a8m
ssh-keygen -t ed25519 -N '' -C "alt8mail-$(hostname)" -f /etc/a8m/github_readonly
chmod 0600 /etc/a8m/github_readonly
cat /etc/a8m/github_readonly.pub

Add the public key in GitHub under Repository → Settings → Deploy keys → Add deploy key. Name it alt8mail-server and leave Allow write access off. Then test the key and clone the immutable release tag:

server · test and clone v0.3.12
GIT_SSH_COMMAND='ssh -i /etc/a8m/github_readonly -o IdentitiesOnly=yes -o StrictHostKeyChecking=accept-new' ssh -T git@github.com
GIT_SSH_COMMAND='ssh -i /etc/a8m/github_readonly -o IdentitiesOnly=yes -o StrictHostKeyChecking=accept-new' \
  git clone --branch v0.3.12 git@github.com:CryptRoute/Alt8Mail.git /root/Alt8Mail
cd /root/Alt8Mail
git describe --tags

GitHub shows a success message instead of a shell, so a nonzero exit from ssh -T is normal. If it reports Permission denied, the key is not on this repository or organization SSO needs the deploy key authorized.

Option B · Copy a tagged source archive over SSH

If the cloud server must not connect to GitHub, create an archive from the immutable tag on this workstation and copy it directly over SSH.

workstation · archive and copy
git archive --format=tar.gz --prefix=alt8mail-0.3.12/ -o dist/alt8mail-0.3.12-source.tar.gz v0.3.12
scp -P 22 -i "$HOME/.ssh/alt8mail_server" dist/alt8mail-0.3.12-source.tar.gz root@YOUR_SERVER_IP:/root/
server · extract the tagged source
cd /root
tar -xzf alt8mail-0.3.12-source.tar.gz
cd alt8mail-0.3.12

The archive contains only tracked files from the tag. It excludes ignored local secrets, the data/ workspace and uncommitted changes. It is source-only, so the installer downloads Go and builds the binaries. The installer generates /etc/a8m/github_readonly; add its .pub to GitHub after installation. If the server can never reach GitHub, updates stay manual: repeat this archive and copy step for each release.

On PowerShell, use $HOME\.ssh\alt8mail_server for the key path, or omit -i if your default key is configured. Use ssh -p and scp -P for a nonstandard SSH port.

Run the installer

Run this as root. If you sign in with a sudo account, use sudo bash install.sh.

bash · install 0.3.12
bash install.sh \
  --domain example.com \
  --hostname mail.example.com \
  --admin-name "Jane Doe" \
  --admin-email owner@example.com \
  --tenant-name "Example Corp" \
  --tenant-slug example \
  --control-email sysadmin@example.com \
  --tls letsencrypt \
  --tls-email admin@example.com
FlagWhat it sets
--domainBare mail domain used in addresses. The owner address must use this domain.
--hostnameMX target and TLS name. Defaults to mail.<domain>.
--admin-email, --admin-nameFirst tenant owner identity.
--tenant-name, --tenant-slugOrganization display name and lowercase identifier.
--control-emailFirst System Control superadmin. Separate from webmail.
--tls letsencrypt, --tls-emailPublic certificate and Let's Encrypt account email.
--non-interactiveOptional. Fail instead of prompting if a required value is missing.

Do not use --skip-packages on a real host. Do not use --tls selfsigned for production unless you are deliberately working in a lab and will replace the certificate before users arrive.

The installer is safe to re-run for repair.It preserves generated secrets and existing accounts, but it reapplies its own nginx, Postfix and UFW configuration. Review custom changes before re-running it.

What the installer changes

01
Installs the Debian mail stack.

PostgreSQL 15, Redis 7, Dovecot, Postfix, Rspamd, ClamAV, nginx, certbot, fail2ban and supporting tools.

02
Sets the host identity.

Hostname, UTC and, when needed, a 2 GiB swap file.

03
Creates the database and first tenant.

Database a8m, application and mail roles, migrations, tenant, domain, owner and mailbox.

04
Installs the application.

Release under /opt/a8m/current, environment under /etc/a8m, secrets under /opt/a8m/secrets.

05
Wires mail delivery.

Dovecot SQL authentication, Postfix virtual domains, Rspamd DKIM signing, ClamAV scanning and LMTP delivery.

06
Obtains TLS and starts services.

Certificate for both names, renewal hook, systemd units and background DKIM/mailbox provisioners.

07
Opens the firewall.

UFW reset, SSH port kept, mail/web/control ports opened. Provider firewall still has to match.

08
Writes the hand-over files.

Root-only credentials and DNS records, plus an updater SSH key to register as a read-only deploy key.

The installer does not finish your DNS or provider setup.It does not create registrar records, set reverse DNS, open the provider firewall, harden SSH, create offsite backups, or create your staff accounts. Those are Phases 04 and 05.

Verify the stack

The installer ends with installation complete and prints the webmail and control URLs. If it reports a failed health check, stop and read the log before changing anything.

bash · health checks
systemctl is-active postgresql redis-server dovecot postfix rspamd clamav-daemon nginx a8m-server a8m-admin alt8mail-control
curl -fsS https://mail.example.com/api/health
curl -fsS http://127.0.0.1:8081/api/health
curl -kfsS https://127.0.0.1:8808/healthz

Every service should print active, the public health endpoint should return JSON with "ok":true, and the admin and control health endpoints should answer. The -k flag is only for the loopback control check; browse to the panel by hostname.

If the installer exited at the service-check stage:

bash · diagnose a failed install
tail -n 100 /var/log/a8m-install.log
systemctl --failed
systemctl status clamav-daemon clamav-freshclam --no-pager

ClamAV's first signature download can take several minutes on a new host. Wait for clamav-daemon to become active, then re-run the installer. Do not delete the release or the secrets directory to start over.

Record the credentials and register the update key

bash · hand-over files
less /root/alt8mail-initial-credentials.txt
cat /etc/a8m/github_readonly.pub

Copy the credentials into your password manager over an SSH session you control. The file contains the owner web password, owner mailbox password, System Control email and password, and the paths to the secret store. It is written only when it does not already exist, so a repair run does not overwrite your copy.

Register the public key as a read-only deploy key on the repository: Repository → Settings → Deploy keys → Add deploy key, with write access off. If you installed from your own fork or mirror, edit /etc/a8m/update.conf and set A8M_REPO before relying on updates.

You are done with Phase 02 when every service is active, all health endpoints answer, and your credentials are stored.

Phase 03 · First sign-in

Open all three doors, separately.

The webmail, customer admin and System Control are separate sessions. Sign in to each one deliberately and verify the identity before you change policy.

Mailbox plane https://mail.example.com/ Webmail

Owner email plus the generated owner web password.

Administration plane https://mail.example.com/admin/ Customer admin

Same Alt8Mail identity, separate admin session and CSRF cookie.

Host control plane https://mail.example.com:8808/ System Control

Separate control account. Root-equivalent access, so restrict it.

Webmail as the owner

Open https://mail.example.com/ and sign in with the owner email and owner web password. The installer-created owner has a generated password and is not forced through the onboarding password-change screen. Treat it as a break-glass credential.

  1. Open Settings → Account and set the display name.
  2. Open Settings → Appearance and Settings → Regional for theme, time zone and formats.
  3. Open Settings → Security and enroll an authenticator or passkey. Save the recovery codes offline.
  4. Store the generated owner password in your vault.
  5. Create a named admin account for daily administration instead of sharing the owner.
To rotate the owner password, use Customer admin → Users → owner → Reset password. The reset signs out existing sessions. Sign back in with the temporary password, then complete the forced change at the next webmail sign-in. The new web password also rotates the Dovecot mailbox password, so mail clients use the new credential afterward.

Customer admin

Open https://mail.example.com/admin/ and sign in with the same owner identity. Include the trailing slash. The installer owner has system-administrator entitlement, so the console can switch tenants.

For day-to-day work, create a named administrator with only the permissions they need. The console supports owners/admins, tenant-scoped custom roles, and member/readonly accounts. The owner remains the break-glass identity.

System Control

Open https://mail.example.com:8808/ and sign in with the control email and password from the credentials file. Use the hostname, not the bare IP. The certificate is issued for the mail hostname, so browsing by IP will produce a browser warning.

  1. Change the control password.
  2. Enable TOTP and store the recovery codes offline.
  3. Create a named operator account instead of sharing the superadmin.
  4. Restrict port 8808 to your administration network.
  5. Review Server & network and TLS before making changes.
System Control is root-equivalent.It can start and stop services, edit Postfix configuration, read logs, issue certificates, run a terminal and restore backups. A compromised superadmin session is as serious as compromised root SSH.

Credential map

CredentialUsed forNotes
Owner web passwordWebmail and customer adminGenerated by the installer; store in your vault
Owner mailbox passwordIMAP, POP and SMTPUsed until the first web password change; then the web password is synced to Dovecot
Control passwordSystem Control onlySeparate identity, separate audit and sessions

You are done with Phase 03 when all three doors open, and you know which identity owns each one.

Phase 04 · Secure it

Close the doors you do not need.

A fresh installation is functional, not finished. The owner, the admin console, SSH and the root-level control panel all need deliberate protection before real users arrive.

Put credentials and MFA in order

  • Store the initial credentials file in a password manager, not a shared drive.
  • Enable TOTP for the owner, every customer admin and every System Control operator.
  • Store recovery codes offline, separate from the authenticator device.
  • In Customer admin → Policies → Security, turn on MFA for administrators first, then for all users once your pilot users have enrolled.
  • Set an admin idle timeout and session lifetime that match your organization's policy.
Do not enable an IP allowlist until you have tested it.Confirm your own egress address and test with a second administrator. A bad allowlist can lock out the console while SSH remains your only recovery path.

Harden SSH

The installer opens your current SSH port; it does not change sshd_config. Add and test a key before applying a stricter policy.

workstation · add a key, then harden
ssh-keygen -t ed25519 -C "you@workstation"
ssh-copy-id -i ~/.ssh/id_ed25519.pub root@YOUR_SERVER_IP
ssh root@YOUR_SERVER_IP '
  install -m 0644 /opt/a8m/current/deploy/ssh/99-alt8mail-hardening.conf /etc/ssh/sshd_config.d/ &&
  sshd -t &&
  systemctl reload ssh
'

The shipped drop-in disables external password and keyboard-interactive authentication, keeps key-based root access for break-glass use, and allows password authentication only on loopback so the System Control terminal can work. Keep an existing root session open until you have verified a new key-based session. If you use a non-root sudo account daily, create and test it before disabling root key access.

Restrict System Control

The installer opens 8808/tcp to every source. Restrict it at both the host and provider firewalls:

bash · restrict 8808
ufw delete allow 8808/tcp
ufw allow from YOUR_ADMIN_IP to any port 8808 proto tcp
ufw status verbose

Use a single trusted IP or a VPN egress range. Keep SSH access open while you test. Do not disable TLS verification to avoid a certificate warning; fix the certificate or use the correct hostname instead.

Treat the customer admin as an administrative surface

/admin/ is served on the same public hostname as webmail. Do not leave it publicly reachable without MFA and a network policy. Choose one of these:

  • Put /admin/ behind your VPN or zero-trust proxy.
  • Restrict access with an nginx allowlist at the edge.
  • Set a tested admin IP policy in Policies → Security.
  • Publish the console on a separate admin.example.com hostname with its own certificate and network controls.

The project's own guidance is explicit: do not expose /admin/ publicly on a production mail host without admin policy and network controls.

Mirror the firewall and keep secrets private

  • UFW is the host firewall, not the cloud firewall. Make the provider security group match the port table.
  • /opt/a8m/secrets is mode 0700 and owned by the a8m service account. Do not loosen it.
  • /etc/a8m/app.env and /etc/a8m/control.env contain database and signing secrets. Keep them root-owned and mode 0640/0600.
  • Only System Control runs as root because it manages host services. That is why its port must be restricted.

You are done with Phase 04 when MFA is on, SSH is key-based, 8808 is restricted and the admin surface has a network boundary.

Phase 05 · Make mail flow

Publish the records and prove both directions.

Mail is not working because the web page loads. It is working when an external server can deliver to you, your server can deliver to an external provider, and the receiving side reports SPF, DKIM and DMARC passing.

Add the mail DNS records

Use the live domain drawer in Customer admin → Domains as the source of truth. The installer's /root/alt8mail-dns-records.txt is an initial convenience; the drawer also shows the ownership record and any later changes.

TypeNameValueNotes
MXexample.com10 mail.example.com.One MX is enough for a single host
TXTexample.comv=spf1 mx -allExactly one SPF record at this name
TXTa8m._domainkey.example.comv=DKIM1; k=rsa; p=...Copy the full value from the admin drawer
TXT_dmarc.example.comv=DMARC1; p=none; rua=mailto:dmarc@example.comStart at p=none, then tighten
TXT_a8m-verification.example.coma8m-verify=TOKENProves ownership; add it for the primary domain too

The DKIM key is generated after the domain exists. If the drawer still says Provisioning, give the timer a minute or start the provisioner:

bash · provision DKIM
systemctl start a8m-dkimprovision.service
systemctl status a8m-dkimprovision.service --no-pager

The timer runs every minute and retries failures. Copy the DKIM TXT value exactly; a truncated or reformatted value will fail verification. The default selector is a8m.

MTA-STS is optional and comes later.Enable it only after basic mail and HTTPS work. It needs an _mta-sts TXT record and an HTTPS policy served for mta-sts.example.com with a trusted certificate. The admin drawer shows the exact expected values.

Verify DNS and TLS

bash · DNS checks
dig +short MX example.com
dig +short TXT example.com
dig +short TXT a8m._domainkey.example.com
dig +short TXT _dmarc.example.com
dig +short TXT _a8m-verification.example.com

Then open the domain in the customer admin and choose Run DNS verification. Aim for green checks on ownership, MX, SPF, DKIM and DMARC. MTA-STS can remain disabled until you are ready to operate it.

bash · TLS checks
curl -I https://mail.example.com/
echo | openssl s_client -connect mail.example.com:443 -servername mail.example.com 2>/dev/null \
  | openssl x509 -noout -issuer -subject -dates

The issuer should be a public CA, the subject should cover mail.example.com, and the expiry should be in the future. Let's Encrypt renewal is handled by certbot.timer; keep port 80 open for the webroot challenge. Inspect the inventory and run a dry run in System Control → TLS.

Test mail from outside

Do not test only from the same host. Loopback delivery can succeed while public DNS or port 25 is broken.

  1. Send from an external mailbox to owner@example.com.
  2. Confirm it arrives in webmail.
  3. Reply from webmail to the external address.
  4. In the delivered message's original headers, confirm spf=pass, dkim=pass and dmarc=pass for your domain.
  5. Check the queue and logs if anything is delayed.
bash · queue and mail logs
mailq
journalctl -u postfix -u dovecot -u rspamd -n 100 --no-pager
tail -n 100 /var/log/mail.log
Queued outbound mail with connection timeouts usually means outbound port 25 is blocked. Ask the provider to unblock it, or configure a smarthost in System Control → Delivery. Inbound mail that never reaches the logs is an MX, inbound-25 or provider-filtering problem.

You are done with Phase 05 when an external round-trip works, all three authentication checks pass and the queue is empty.

Phase 06 · Add people

Create a pilot before you create a company.

Start with one named administrator and one pilot user. Prove the onboarding, mail client and external delivery experience before importing a directory.

Create a named administrator

In Customer admin → Users → New user, create an administrator with a real name and address. Give the account only the role it needs. Admin-created users go through the guided onboarding flow on first sign-in: display name, time zone, language, theme and password change. Enroll MFA before adding more administrators.

Import users from CSV or XLSX

Use Customer admin → Users → Import users. Full name and email are required. Unknown roles become member.

What users experience

  • New users must complete onboarding before they can use the mailbox.
  • They set their display name, time zone, language, theme and a new password.
  • The new web password is synchronized to Dovecot, so the same credential works for webmail and mail clients.
  • MFA enrollment can be encouraged during onboarding and required by policy afterward.
  • Recovery codes are shown once; users must store them.

Policy checklist

  • Security: MFA for admins then all users; password length and history; session limits; admin IP ranges only after testing.
  • Mail: IMAP/POP access, SMTP access, forwarding, retention, attachment limits and Junk release policy.
  • Sharing and directory: external sharing, directory visibility and profile editing.
  • Branding: organization name, logo and colors.
  • AI assistant: optional. Configure an OpenAI-compatible endpoint or Anthropic, then use Save & test. The API key is sealed and never returned to the browser; keep policies.manage restricted.

The default Junk behavior lets users release their own Junk. If you want administrator-only release, enable Restrict Junk release to administrators. Users then see the administrator-release state and an authorized administrator handles the quarantine queue.

Pilot gate: one user completes onboarding, signs in with a mail client, sends to an external address and receives a reply with SPF, DKIM and DMARC passing. Only then import the rest of the company.

You are done with Phase 06 when the pilot user can work entirely through Alt8Mail without an administrator touching the server.

Phase 07 · Operate and recover

Make updates boring and recovery real.

The installation is a starting point. The operating habits below decide whether the platform is still healthy six months from now.

Application updates

Application updates are tag-based and transactional:

bash · update Alt8Mail
sudo alt8mail-update --check
sudo alt8mail-update

The updater fetches the latest stable tag, builds it, backs up the database and configuration under /var/backups/alt8mail/update-TIMESTAMP, applies migrations, switches the release symlink and checks all three services. If readiness fails, it restores the previous release and database.

bash · update evidence
tail -n 100 /var/log/alt8mail-update.log
ls -lt /var/backups/alt8mail | head
cat /opt/a8m/current/VERSION

Run updates in a maintenance window. Mail queues rather than message content are affected during the short service restart. Do not edit files under /opt/a8m/current; it is a release symlink and will be replaced.

Operating-system packages are separate: use System Control → Infrastructure → Software updates for apt packages and reboot status.

Backups: two layers, not one

Layer 1, the control-plane archive. System Control → Infrastructure → Backups creates a .tar.gz of selectable contents: PostgreSQL, Postfix, Dovecot, DKIM, Let's Encrypt and Maildirs. The default selection does not include Maildirs; select Maildir message stores for a full mail backup.

Layer 2, the critical configuration and secrets. The control-plane archive does not include /opt/a8m/secrets or /etc/a8m. Without those, a full disaster recovery is incomplete.

bash · critical config archive
tar -C / -czf /root/alt8mail-critical-$(date -u +%F).tar.gz \
  opt/a8m/secrets \
  etc/a8m \
  etc/nginx \
  etc/redis/a8m.conf \
  etc/ssl/alt8mail
chmod 600 /root/alt8mail-critical-$(date -u +%F).tar.gz

Download the control-plane archive from the Backups table in System Control. Then pull the critical configuration archive over SSH:

workstation · pull the backup
scp root@YOUR_SERVER_IP:/root/alt8mail-critical-*.tar.gz ./
The control-plane archive is a plain .tar.gz.It is not encrypted at rest. Move it over SSH or TLS, then store it encrypted in a vault or object store you control. A backup on the same lost server is not disaster recovery.

Test a restore on a separate Debian host before you need one. At minimum, verify that the database dump restores, the Maildir tree is readable and the restored host can start the three services with the same secrets.

Monitor what fails first

  • System Control dashboard: service health, CPU, memory, disk, mail volume, queue, certificate expiry and update state.
  • Notifications: configure at least one handle (email, Slack, Discord, Telegram or webhook) and send a test.
  • Queue: investigate deferred mail before it becomes a delivery incident.
  • Disk: watch /var/vmail and /var/backups/alt8mail; both grow.
  • TLS: keep port 80 open and check the certificate inventory and renewal state.
  • Logs: Postfix, Dovecot, Rspamd and the three Alt8Mail services are in journald and /var/log/mail.log.

TLS renewal

When installed with Let's Encrypt, certbot.timer is enabled and a deploy hook copies the renewed certificate to nginx, Postfix, Dovecot and System Control and reloads the affected services. Keep port 80 reachable.

bash · certificate renewal check
systemctl list-timers 'certbot*' --no-pager
certbot renew --dry-run

The dry run should complete without changing the live certificate. If you replace certificates with a CA-issued pair, use System Control → TLS to import and assign them rather than editing certificate paths by hand.

Disaster recovery outline

  1. Build a new Debian 12 host with the same hostname and domain plan.
  2. Install the same Alt8Mail release.
  3. Stop the application and mail services.
  4. Restore the PostgreSQL dump, /var/vmail, mail configuration and /opt/a8m/secrets.
  5. Restore /etc/a8m, TLS material, nginx and systemd units.
  6. Start the stack and verify health, login, inbound mail, outbound mail and DKIM.
  7. Repoint DNS and reverse DNS only after the restored host is healthy.

Rehearse this on a scratch host. Do not make the first restore attempt during an outage.

You are done with Phase 07 when a backup has been downloaded, a restore has been rehearsed and someone is responsible for updates and alerts.

Troubleshooting

Start with the layer that failed.

Most first-install failures are DNS, provider firewall or a service that has not finished starting. Read the log before changing configuration.

Let's Encrypt did not issue a certificate

Check both A records, the proxy status for mail, port 80 and any CAA record. Inspect /var/log/letsencrypt/letsencrypt.log. If the host fell back to self-signed, fix DNS and port 80, then re-run the installer with --tls letsencrypt or issue a certificate through System Control → TLS.

The installer stopped at a health check

Read /var/log/a8m-install.log and run systemctl --failed. On a fresh host the usual cause is ClamAV still loading its first signature database. Wait for clamav-daemon to become active, then re-run the installer. Do not delete the release or the secrets directory to start over.

Webmail loads but the owner cannot sign in

Use the exact owner email and the web password, not the mailbox password. Check systemctl status a8m-server and journalctl -u a8m-server -n 100. Confirm the account is active in the customer admin. If the owner password is lost, use the customer admin reset flow.

/admin/ returns 404 or cannot be reached

Include the trailing slash: https://mail.example.com/admin/. Check systemctl status a8m-admin, curl http://127.0.0.1:8081/api/health and the nginx configuration. The admin UI is served by the Go admin binary, not as a static file.

System Control will not open

Use https://mail.example.com:8808/, not port 88008 and not the plain HTTPS port. Check the provider firewall, ufw status and curl -kfsS https://127.0.0.1:8808/healthz. A warning when browsing by IP is expected if the certificate is issued only for the hostname. Restrict 8808 rather than disabling TLS verification.

Domain verification fails

Read the per-check details in the domain drawer. Common causes: missing or wrong ownership token, MX not pointing at the mail hostname, multiple SPF records, a truncated DKIM p= value, or an invalid DMARC policy. Wait for propagation, then run verification again. The installer creates the initial domain as manual; the real records are still required for reliable mail.

Inbound mail does not arrive

Check MX, inbound port 25 at the provider, journalctl -u postfix, /var/log/mail.log and mailq. A missing MX or a provider-level port-25 block is more likely than a Dovecot problem on a new installation.

Outbound mail stays queued

Check outbound port 25 first. Then check PTR, SPF, DKIM and DMARC, and read the queue reason with mailq. A provider that blocks outbound 25 can be handled with a smarthost in System Control → Delivery. A provider that blocks inbound 25 cannot receive direct MX mail and needs a different host or a front relay.

A mail client rejects the password

Use the full email address as the username and the current mailbox password. Use IMAPS 993 and submission 587 with STARTTLS. Confirm IMAP/POP access is enabled in policy. After a web password change, use the new password; the mailbox hash is synchronized. App passwords are for CalDAV/CardDAV, not IMAP/SMTP.

An application update fails

Confirm /etc/a8m/github_readonly.pub is registered as a read-only deploy key on the configured repository, then read /var/log/alt8mail-update.log. The updater restores the previous release and database when readiness fails; the backup path is printed in the failure message and in the log.
